# Website visitor accounts

Backy implements separate, persisted website memberships and opaque visitor sessions. A visitor is never a CMS operator. The API requires a published site, enabled visitor policy, exact approved website origins and return URLs, a database with migrations through `028_visitor_pkce_flows.sql`, and Backy's server-configured Supabase Auth provider. Unconfigured/demo accounts fail closed. No production provider configuration or account creation is implied by source tests.

Start with `GET /api/sites/:siteId/agent-handoff` and read `data.handoff.visitorAccounts`. It exposes sanitized policy, methods, field names, runtime requirements and pending integration boundaries. Manifest and OpenAPI mirror that policy. The site OpenAPI document contains the ten standard account operations and `Visitor*` component schemas; visitor responses intentionally do not require the operator API's `requestId` field.

| Operation | Input | Successful result |
| --- | --- | --- |
| `POST /visitor-auth/register` | `{email,password,returnUrl,displayName?,authFlow?:"pkce"}` or `{accessToken,displayName?}` | `200 {success:true,data:{member,expiresAt}}` plus visitor cookie, or uniform `202 {success:true,data:{confirmationRequired:true,message}}` |
| `POST /visitor-auth/callback` | `{code,state,returnUrl}` | Confirm server-held signup flow, verified member and visitor cookie; never return provider tokens |
| `POST /visitor-auth/login` | `{email,password}` | Existing active same-site member and cookie; never enrolls another site |
| `GET /visitor-auth/session` | Site visitor cookie or opaque `bkv_` header/bearer | `{success:true,data:{member}}` |
| `PATCH /visitor-auth/profile` | `{displayName}` only; trim to at most 120 UTF-16 code units, reject control characters; empty clears | `{success:true,data:{member}}`; current active same-site session rechecked atomically, no new session issued |
| `POST /visitor-auth/logout` | Optional current visitor credential | `{success:true,data:{loggedOut:true}}`; revoke current session and clear cookie |
| `POST /visitor-auth/recovery` | `{email,returnUrl,authFlow?:"pkce"}` | Uniform `202 {success:true,data:{message}}`; does not certify account existence or mail delivery |
| `POST /visitor-auth/reset-password` | `{accessToken,recoveryToken,password}` or `{code,state,returnUrl,password}` | `{success:true,data:{passwordReset:true,message}}`; clear cookie, then sign in again |

The table's paths are relative to `/api/sites/:siteId`. `member` contains only `id`, `siteId`, `email`, `displayName`, `status`, `createdAt` and `updatedAt`. Provider subjects, roles, raw provider tokens and session hashes are excluded. The provider user access token in enrollment/reset requests is verified server-side through the provider's user endpoint; client claims/metadata do not confer authority.

All operations require an exact approved `Origin`, or a same-origin browser request carrying `Sec-Fetch-Site` plus `Referer`. Backy does not infer approval from a caller-supplied host. JSON requests are limited to 16 KiB before provider work. New passwords require at least 12 characters and at most 1024 UTF-8 bytes. Durable budgets constrain site, attributed IP and email operations. Production proxy/IP attribution needs deployment certification; the site budget still bounds requests when IP attribution is unavailable.

Sessions use random 256-bit `bkv_` tokens; only SHA-256 hashes persist. Cookies are site-derived, host-only, HttpOnly, SameSite=Lax and Secure in production, with one-hour expiry. Every response is private/no-store. Only visitor cookies/headers/bearers are considered. Operator cookies, keys and provider tokens cannot substitute for a visitor session. CMS-profile admission denial checks provider subject and normalized email and fails closed on repository failure.

Authenticated forms and signed-in comments resolve this same site membership. Forms remain subject to their consent/captcha/scanner/storage policies. `adminOnly` forms still require an operator with the relevant permission. Comments derive identity and attribution server-side and keep visitor member IDs private in public serialization. Persistence locks the member row, rechecks active status/site/operator exclusion, and serializes against suspension; a suspended membership cannot finish an attributed write after suspension commits. Existing anonymous forms/comments retain their guest paths.

## SDK and separate website frontend

`@backy/sdk-js` provides `visitorRegister`, `visitorCallback`, `visitorLogin`, `visitorSession`, `visitorLogout`, `visitorRecovery`, `visitorResetPassword` and `visitorUpdateProfile`, with generated request/response types. The visitor transport ignores client-wide operator headers and credentials, uses no-store, rejects redirect following and accepts only explicit visitor options. `sessionToken` is for a trusted server that already holds the website's opaque visitor token; do not return it to browser JavaScript. Browser transports should use a same-origin website BFF or reverse proxy. A Node SDK call does not automatically persist cookies; a trusted BFF must capture and reissue only the site's cookie.

The checked Next.js starter supplies `/account`, `/api/backy-account/:operation`, and a server-only bridge. Configure matching public URL values `BACKY_VISITOR_FRONTEND_ORIGIN` and `BACKY_VISITOR_RETURN_URL=https://<website-origin>/account`; approve them in the selected site's visitor policy. The bridge resolves canonical site identity through handoff, strips unknown request fields, fixes the return URL, checks the incoming website origin before forwarding and reissues only that site's valid visitor cookie. Operator/provider cookies, upstream private metadata and raw upstream error text are never relayed.

The checked account BFF selects `authFlow:"pkce"` for signup and recovery. Backy stores a random S256 verifier in a private 15-minute flow bound to the canonical site, exact initiating origin, approved return URL, purpose and expected email. Only its opaque state appears in the email return URL, alongside `backySiteId` and `backyVisitorFlow`. Each flow has its own verifier, so overlapping emails do not overwrite earlier flows. The account screen removes query/fragment values before network work or errors and never uses browser token storage or forwards refresh tokens.

Signup sends `{code,state}` through the website BFF, which fixes `returnUrl`; Backy consumes the flow atomically before the provider exchange, verifies the resulting identity through the provider user endpoint and issues only a site visitor cookie. Recovery holds the code/state only in component memory until password submission, then sends `{code,state,password}`; the server exchanges it, rechecks the original active membership, revokes the subject’s visitor sessions/challenges and changes the provider password. Recovery never creates a login session. A wrong site, origin, URL or purpose cannot consume the flow. Replays, expired flows, unavailable persistence/provider, mixed token/code payloads and unconfirmed/operator identities fail closed. Failed or uncertain exchanges consume the flow and require a new email; suspension, access removal, email changes and subject session revocation remove applicable pending flows.

[Supabase PKCE documentation](https://supabase.com/docs/guides/auth/sessions/pkce-flow) specifies a five-minute, one-use authorization code; submit a recovery password promptly after opening the email. Its [primary client implementation](https://github.com/supabase/auth-js/blob/master/src/GoTrueClient.ts) sends `code_challenge`/`code_challenge_method:"s256"` on signup/recovery and `auth_code`/`code_verifier` to `token?grant_type=pkce`. Backy supplies only a verifier created and consumed through its own persisted flow. Existing implicit signup/recovery callbacks remain supported for older emails. Real confirmation email, provider redirect allowlists (including Backy’s state query), SMTP delivery, recovery callback and deployed browser behavior still require certification before launch.

The starter forwards the website’s HttpOnly visitor cookie through same-origin form and comment BFF routes only after rechecking canonical site identity and the exact approved account origin/return URL. The current form definition controls declared fields; multipart file parts retain their bytes through Backy’s existing private scanner/storage pipeline, and only server-generated attachment references persist. Public comments expose approved records and current site policy; submissions cannot forward moderation privileges or owner identity. The backend derives visitor attribution and remains the admission authority. Public guest forms/comments continue according to policy without requiring accounts to be enabled.

Self-service display-name editing is implemented in the checked account page and uses only the active site visitor session. The persisted update locks the member and exact session, then rechecks current expiry, revocation, published/enabled website admission and operator exclusion before changing the name. It does not rotate sessions, change email or rewrite historical comment author text.

Operator display-name edits, suspension/reactivation, session revocation and retained access removal are implemented in the site’s Website visitors panel. Two-step self-service email changes are implemented in source; a bounded Owner-confirmed local erasure subset is implemented below; deployed provider integration and downstream erasure remain separate work. Account UI source/SSR and fixture tests do not certify a real signup/login/email callback. CAPTCHA widgets use public site keys and supported provider scripts; production CAPTCHA and attachment storage/scanner certification remain separate gates.

## Private visitor member management

The site workspace’s **Website visitors** panel lists existing memberships with search, status filters and pagination. Every management route requires `sites.configure`, an active operator session or appropriately scoped service key, and current site/team grants. Visitor credentials never authorize these routes. Management requires the persisted database; demo or missing capability fails closed. Accounts may be disabled or a site unpublished while operators manage retained memberships.

| Route relative to `/api/admin/sites/:siteId` | Method | Input / behavior |
| --- | --- | --- |
| `/visitors` | GET | `limit` 1–100 (default 50), nonnegative `offset`, optional `status=active\|suspended\|removed`, literal `search` up to 120 characters; includes `hasMore` |
| `/visitors/:memberId` | GET | Same-site member profile; no provider subject or session values |
| `/visitors/:memberId` | PATCH | `{displayName?,status?:"active"\|"suspended"}`; email/provider identity/operator roles cannot change |
| `/visitors/:memberId/revoke-sessions` | POST | Empty JSON `{}`; revoke this site’s sessions and recovery challenges |
| `/visitors/:memberId` | DELETE | `{confirmRetention:true}`; remove access with a retained `removed` tombstone |

Migration `018_visitor_membership_access_removal.sql` permits the removed state and indexes the site management inventory. Suspension, explicit revocation and access removal delete same-site session and recovery-challenge rows while holding the same member row lock as attributed content admission. State change and a safe activity audit commit in one transaction; failure rolls everything back. Reactivation requires a fresh sign-in and never restores old sessions. Removed memberships cannot be edited/reactivated or automatically reenrolled; existing provider/website uniqueness remains intact. Other websites’ memberships and sessions remain unchanged.

**Remove access is not personal-data erasure.** Member email/display name and attribution remain, as do historical comments, form submissions, contacts and private attachments under their existing retention policies. Changing display name does not rewrite historical comment author text. The shared provider identity and credentials remain untouched. A distinct, reviewed erasure/provider-account lifecycle is still required where applicable. Every management response is private/no-store and states this retention boundary explicitly.

`@backy/sdk-js` exposes `listAdminVisitorMembers`, `getAdminVisitorMember`, `updateAdminVisitorMember`, `revokeAdminVisitorMemberSessions` and `removeAdminVisitorMemberAccess` with generated standard OpenAPI types. These are trusted operator/server operations; do not ship operator credentials in the public account frontend.

## Shared provider and origin boundaries

Enrollment is explicit per website. Same email on another website does not migrate or merge memberships. The configured provider identity, however, has a shared credential: recovery/reset revokes visitor sessions for the subject across all explicitly joined sites before changing that provider password. Backy email changes require fresh password verification and two explicit steps. Initiation revokes all existing subject sessions/recovery before requesting provider confirmation. Completion freshly verifies the confirmed email/password and an existing active membership of the selected site, synchronizes current email across existing active/suspended memberships, and revokes sessions again. Names, IDs, statuses, removed memberships and historical attribution stay unchanged; no enrollment or new session occurs. Ordinary sign-in is required. Provider email changes outside Backy do not automatically update/merge memberships.

Unrelated websites must use distinct approved browser origins. Cookie names/site database keys cannot isolate scripts co-hosted on the same origin. Existing CMS operators are denied visitor enrollment/recovery/reset, but conversion of a historical visitor into an operator requires a separately certified conversion/provider policy: historical provider-issued recovery credentials outside Backy's guarded APIs are not invalidated by an application lookup. A separate visitor provider project is one possible boundary; no such project was provisioned here.

## Visitor email change

`POST /api/sites/:siteId/visitor-auth/email-change` accepts exactly `{newEmail,currentPassword,returnUrl}` and requires the current opaque website session plus a fresh provider password. The server derives the old identity. `202` returns `{confirmationRequired:true,signInRequired:true,message}`; it does not mean the email changed. Use an exact approved return URL from the site handoff. Sessions remain revoked if the provider request subsequently fails.

After following all provider confirmation emails, `POST /api/sites/:siteId/visitor-auth/confirm-email-change` accepts exactly `{email,password}`. The provider identity must have a confirmed email and an existing active selected-site membership. `200` returns `{emailChanged:true,signInRequired:true,message}` and clears the site cookie. There is no automatic enrollment or login. Retry the completion after both confirmation steps if the provider still reports an unconfirmed or old email; callback credentials/provider200 alone do not establish completion. No pending email or provider token is persisted.

The checked starter scrubs callback query/fragment credentials before network or UI, opens a signed-out completion form for `email_change` or partial confirmation, clears password fields after every attempt, retains only the safe email draft, and keeps ordinary login available. Its BFF derives the return URL from the approved server-side handoff context and propagates only the canonical site cookie clearing, including failures after revocation. The SDK exposes `visitorEmailChange` and `visitorConfirmEmailChange`; operator/provider credentials remain excluded. Source and synthetic fixture checks do not certify real confirmation email, provider settings or deployed browser behavior.

## Private visitor privacy impact review

`GET /api/admin/sites/:siteId/visitors/members/:memberId/privacy-impact` is a read-only, selected-site/member review for an active Owner cookie session with `users.view` and current central site admission. Explicit bearer/session headers and API/service keys are refused before usage or aggregate reads, even beside an Owner cookie. The route accepts no body or query parameters and returns a private/no-store `{success,requestId,data}` envelope. The persisted adapter is required; missing capabilities fail closed. Retained active, suspended and removed memberships can be reviewed while their website is unpublished or visitor accounts disabled.

The `backy.visitor-privacy-impact.v1` data contains the canonical site/member IDs, member status, `observedAt`, `reviewMode:'read-only-point-in-time'` and counts for exact `visitorMemberId` comments and form submissions. `linkedContacts` counts copies linked by `sourceSubmission`; this link does not establish exclusive ownership. Comment and form delivery aggregates each contain `total`, `pending`, and `unknownOutcome`, where unknown outcome means the durable journal's stored `uncertain` state. A single database statement provides the point-in-time aggregate; it is not a version token for later deletion or a retention policy.

No email matching, names, comment bodies, submission values, file bytes, arbitrary metadata or provider identity are exported. Fixed retained-category labels describe existing membership, comment/moderation, submission/files/admin metadata, contact-copy and delivery-evidence retention boundaries; they do not claim that private fields or files were inspected. Downstream provider copies, legacy activity logs and outbox provenance remain unknown. The response explicitly sets `emailMatchedOwnership`, `contentInspected`, `erasurePerformed` and `providerChanged` to false. It neither deletes data nor certifies privacy erasure.

The SDK's `adminVisitorPrivacyImpact(memberId,{siteId,requestId})` uses isolated Owner-cookie transport on the approved same-origin admin rewrite. It ignores inherited operator/key headers and has no body, export or mutation fallback. OpenAPI describes field contracts only; public discovery does not include a member's review or sensitive payload. Source and disposable HTTP/database fixtures remain separate from deployed Owner acceptance.

## Selected-website local erasure

The Website visitors panel now offers **Local erasure** to an active Owner cookie session with `users.delete` and current selected-site admission. This source feature requires PostgreSQL and migration `032_visitor_privacy_erasure.sql`. It does not execute an erasure during source/fixture verification or provision/change a provider account.

The Owner explicitly chooses `comments:"redact"|"retain"`, `submissions:"redact"|"retain"` and `exclusiveContacts:"delete"|"retain"`. The selected membership’s direct email/display name are always redacted, site access and site sessions/recovery/PKCE flows are removed, and a durable fence prevents subsequent attributed admission/follow-ups. Its removed provider-subject tombstone remains to prevent reenrollment. Other websites and the shared provider identity remain unchanged. The final retention choices are immutable for this action.

| Route relative to `/api/admin/sites/:siteId/visitors/members/:memberId` | Request | Result |
| --- | --- | --- |
| `POST /privacy-erasure/preview` | `{choices:{comments,submissions,exclusiveContacts}}` | Counts-only `backy.visitor-erasure-preview.v1`, a five-minute actor/site/member-bound preview ID, fixed retained categories and explicit scope |
| `POST /privacy-erasure/confirm` | `{previewId,confirmLocalErasure:true}` | `backy.visitor-erasure-receipt.v1` with actual redaction/deletion counts, minimal private receipt and retained boundaries |

Both routes reject explicit bearer/session/key headers even alongside a cookie, require the central Owner permission/site/origin admission and return private/no-store responses. Confirmation rereads and locks exact source/contact rows and compares the member, content, contributor and durable delivery snapshot to the preview. A changed/expired/foreign preview fails before writes. Retrying the same confirmed preview returns its durable receipt without executing erasure again. Receipt failure rolls back all local changes. No provider credential, name/email, content/file bytes or source-value payload appears in the preview/receipt.

When selected, comment redaction clears that exact member’s comment body, author identifiers, reports and moderation notes, retaining IDs/thread links/timestamps with a rejected redacted row. Submission redaction clears non-file submitted values, IP/user-agent/request identifiers, review/admin notes and collection-link metadata. Private attachment bytes are **retained under owner retention**: sanitized attachment references remain with unchanged IDs/byte counts/MIME and a generic filename. Existing owner attachment access/storage accounting stays available. Collection records previously copied from those submissions are not erased by this action. Choosing retain keeps the respective source content, but still fences its later writes/copies/deliveries.

Contact deletion requires complete durable contributor provenance: every contributor must be an exact selected-site submission attributed to this member and the contact must never have received a manual/unknown modification. The new persisted contact-share method derives contributors from server-owned submission rows, records every merge and preserves all earlier contributors. Mixed-member/guest contributors, manual modifications and legacy contacts are ambiguous and remain retained. A legacy `sourceSubmissionId` is backfilled as one known contributor only; it never proves earlier merges were absent. No email matching infers ownership. Known member-linked retained contacts are fenced against subsequent sends/merges; contacts without any contributor evidence remain outside proven ownership and coverage.

Persisted submission/comment/contact follow-up gates hold a durable per-site privacy lock through copying or provider execution. Erasure waits for in-flight callbacks; after it commits, those source gates and database write fences reject delayed retries, moderation writes and contact recreation. Existing form/comment retry routes use the same gate; admin submission moderation/contact sharing and contact user/customer promotion are fenced before new copies. Newsletter campaign SMTP uses the contact gate. Follow-up pool admission is bounded; webhook provider calls have a deadline. A delivered copy from before erasure is not recalled. Historical activity/outbox/delivery evidence, newsletter consent/address snapshots, provider copies and unknown legacy downstream copies remain retained or unverified; local erasure is not a full global erasure certificate.

`@backy/sdk-js` exposes `previewAdminVisitorErasure` and `confirmAdminVisitorErasure` through isolated Owner-cookie transport. The checked admin UI defaults every optional category to retain, shows the preview counts/retained categories and requires an explicit acknowledgement before confirmation. Changing the choices invalidates the preview. Context changes discard stale operations. API/source/disposable database and synthetic-browser proof do not authorize a real member erasure or establish deployed behavior.

Verification: `npm run test:visitor-erasure:postgres --workspace @backy/db` runs all migrations in an owned socket-only PostgreSQL cluster and exercises actual repositories with both Postgres.js and native `pg`, exact route wrappers, mixed/manual/legacy contributor retention, chosen retain/redact outcomes, changed/foreign previews, rollback, concurrent follow-up admission, post-erasure fencing, safe projections and RLS. `node packages/sdk-js/scripts/visitor-erasure-smoke.mjs` checks encoded scope and isolated transport after an SDK build. `npm run test:visitor-erasure-rendered --workspace @backy-cms/admin` starts the actual component/client with synthetic HTTP responses only; it performs no database/provider/account mutation.


Selected website/form teardown preserves local privacy evidence. Persisted DELETE admission takes the same durable website lock as contributor creation, erasure, and delayed follow-ups before deactivation, attachment preparation, storage cleanup, or logical deletion. A website with contributor provenance, member fences, or erasure receipts returns `409 VISITOR_PRIVACY_EVIDENCE_REMAINS`; a form with contributor provenance linked through its exact same-site submissions or contacts returns the same actionable denial. Keep the resource archived/inactive until an explicit evidence retention and teardown policy is implemented. Member erasure does not authorize cascading this evidence. Missing capability/migration returns `503 VISITOR_PRIVACY_TEARDOWN_UNAVAILABLE` before cleanup; demo data has no durable privacy ledger. Private attachment bytes and references remain governed by the existing owner retention policy.
