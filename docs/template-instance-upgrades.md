# Reviewed page and blog template instance upgrades

New frontend-template page/blog clones retain `meta.frontendTemplateInstance` (`backy.template-instance.v1`): exact template fingerprint/version, canonical baseline content and its fingerprint, and the original seed context. Baselines contain editable content only; no site settings, provider records or registry credentials are copied. Unsafe credential/prototype keys, oversized content or unsupported depth/value counts refuse cloning/review instead of dropping fields. Theme/font token references remain supported.

Template history keeps its existing registry-only restore behavior. In **Template history → Review revision → Review existing instances**, authors inspect the complete page/post inventory, select ready documents, review that exact selection, then confirm **Upgrade reviewed instances**. No restore or template save automatically updates authored documents. Legacy template-ID-only documents are listed as unpinned and blocked; an earlier baseline cannot be safely inferred. Their editor links remain available for manual work.

`POST /api/admin/sites/{siteId}/templates/{templateId}/instances` accepts `{action: 'review'|'apply', targetRevisionId, selection: [{type: 'page'|'post', id}], reviewVersion?}`. Review requires `pages.view`; apply additionally requires `pages.edit`, and `pages.publish` for selected published/scheduled documents. Status/publication and document identity stay unchanged. The target is an immutable retained same-site revision whose snapshot/fingerprint is verified. Page templates upgrade pages; blog templates upgrade posts. Form definitions use the explicit form boundary documented below; product and section lanes have their own reviewed contracts, and collection definitions use the independent boundary documented below.

Read-only impact review performs a three-way merge between the pinned baseline, current authored content and target seed. Stable element IDs preserve nested compositions and sibling insertion/order. Template-only changes can apply; author-only changes and unknown extensions remain. Different overlapping edits, modified-element deletion, ambiguous array edits and conflicting reordering produce bounded values-free JSON paths. Definitions and values are not guessed or coerced. A template upgrade does not certify component execution, custom scripts or deployed frontend compatibility.

Apply requires the exact `template-instances-v1:` review token (64 lowercase hex). It binds canonical site/design, retained revision, explicit selection and every matching document's full content/metadata/identity/timestamp fingerprint. Changed selection, design or matching inventory returns409 `TEMPLATE_INSTANCE_REVIEW_STALE` before writes. Selected conflicts return422. Request-time permissions remain authoritative; fingerprints are conflict evidence, not credentials.

Each selected document is independently reread and updated through existing content/timestamp CAS. PostgreSQL row admission inserts its baseline revision and changes content/meta in the same transaction; a late write failure rolls back that document and revision. Demo uses its existing synchronous same-process guard and retained baseline revision. Other documents may already have committed when a later document fails: success200 reports `appliedTargets`, `failedTargets` (`CONTENT_CONFLICT`/`WRITE_FAILED`), `outcome`, `completionWarnings` and the concurrency boundary. There is no cross-document transaction or automatic retry. Audit/cache failures retain confirmed content and produce safe warning codes, without claiming a durable retry queue.

Bounds: 64 KiB request, 200 explicit selections, 2,000 matching instances, 100,000 pages/posts per inventory kind, 64 MiB combined reviewed content, 2 MiB per baseline/current/target content, 60,000 JSON values and depth64. Each document exposes at most128 changed paths and64 conflicts; path strings are capped500 characters. Oversized input is413, incomplete/malformed/foreign inventory or unavailable guarded writers503, invalid request/selection400, missing site/revision404, unsupported template/content422, unexpected precommit errors sanitized500. All responses are private/no-store.

## Evidence

- Public `test:template-instances`: actual handler/helpers/retained demo snapshots and persistence, both demo and repository-adapter branches; AJV validates real outcomes against current OpenAPI. 240 checks cover readonly impact, pinned cloning, authored/unknown retention, overlap/legacy refusal, stale review and commit-time conflict, safe outcomes, credential/size limits and early permission denial.
- Admin `test:template-instances`: actual typed transport and production SSR controls; exact review/apply selection, stale/forged-response refusal, cancellation, permission notices and parent-form-safe actions. Browser behavior is separate.
- DB `test:template-instances:postgres`:60 checks in an owned socket-only cluster with22 actual migrations. Actual PostgreSQL handlers/repositories/history verify pinned page/blog upgrades, authored/unknown metadata retention, baseline revisions, independent-connection author conflict and late write/revision rollback. No configured database URL is accepted; the cluster is stopped and removed.
- Existing `test:admin-lifecycle-openapi`124 and `test:admin-content-save-outcomes`240 pass after the provenance hook; the VM loader loads the actual new dependency. Public/admin typechecks and core ESM/CJS/DTS build pass.

Served admin/shared-editor acceptance is being run separately in a disposable fixture. Deployment, provider behavior, owner authentication and the actual custom frontend remain separate acceptance boundaries. General forms/products/sections/collection template upgrades are outside this page/blog contract.

Confirmed page/blog upgrades emit one `site-updated` site webhook per apply request,
with reason `frontendDesign.templateInstanceUpgrade`, exact `appliedTargets` and
applied/failed counts. Review, authorization/validation/conflict refusal, failed-only
apply and already-current instances do not dispatch. A fresh reviewed retry includes
only newly confirmed commits; prior successful targets are not dispatched again.
The payload omits retained baseline content and failed target IDs. Both returned
failed delivery outcomes and thrown journal/delivery errors retain HTTP200 and
confirmed content, adding `TEMPLATE_INSTANCE_WEBHOOK_PENDING` to completion warnings
and setting outcome `partial`. No configured webhook targets (`[]`) is a normal
success. This does not promise automatic replay or durable retry. The actual-handler
template suite covers both adapters and both page/blog types with no provider network.

## Form definition designs and private recovery

Form template review/apply uses the same instance endpoint with explicit `targetType: "form"` and `selection: [{type: "form", id}]`. Even an empty impact selection requires the discriminator. Forms cannot mix page/post/section/product selections. Review requires selected-site `forms.view`; apply additionally requires `forms.edit`, with the exact `template-form-instances-v1:<sha256>` review token. `scanned.forms` reports the complete bounded form inventory. Collection definitions use the independent boundary documented below.

The merge admits compatible presentation changes and retains author-only edits. Field keys, types, required state, options, validation, defaults, unknown field semantics and configured operational bindings cannot be silently changed; findings use `SCHEMA_INCOMPATIBLE` at bounded JSON paths. Apply retains active state, notification destinations, spam/consent policy, contacts/collection behavior, submissions, attachments and delivery/reconciliation evidence. Full form-definition admission detects operational races as well as design races. Inspect `appliedTargets`, `failedTargets`, `completionWarnings` and partial outcome; never automatically replay an apply.

`GET /api/admin/sites/:siteId/forms/:formId/design-versions` requires `forms.view`. It returns `{siteId, formId, currentVersion, pagination, revisions}`. `currentVersion` is `form-v1:<sha256>`; summaries contain only `id`, `createdAt`, `operation`, nullable `templateId`/`targetRevisionId`, and `hasPinnedBaseline`. They contain no historical snapshots or submission values. Newest-first `offset` is 0–1,000,000 and `limit` is 1–100 (default100); follow `pagination.hasMore` and `nextOffset`. SDK: `listAdminFormDesignVersions`.

`POST /api/admin/sites/:siteId/forms/:formId/design-versions/:revisionId/restore` requires `forms.view` and `forms.edit`, and the exact body `{expectedVersion}`. It restores compatible presentation and the matching baseline into the latest form, retaining current field semantics, operational settings and all response/delivery data. The preceding design is saved privately under the same guarded write.200 returns `{siteId, formId, restoredFromRevisionId, form, completionWarnings}`; `form.version` is the new token.409 `FORM_DEFINITION_CONFLICT` requires reload.422 `FORM_TEMPLATE_SCHEMA_INCOMPATIBLE` blocks incompatible recovery. An unavailable private history repository returns503 `FORM_DESIGN_HISTORY_UNAVAILABLE`; no unguarded fallback is authorized. SDK: `restoreAdminFormDesignVersion`. All recovery responses are private/no-store; audit/cache completion warnings after a committed restore do not authorize replay.

Canonical `026_form_design_revisions.sql` is required for database recovery. Its presence and passing source contracts do not prove that migration applied or that these routes are deployed. Record migration, authenticated browser, separate frontend and production/provider evidence independently.

## Collection definition designs and private recovery

Collection template review/apply uses the instance endpoint with explicit `targetType: "collection"` and `selection: [{type: "collection", id}]`, including an empty impact selection. It cannot select collection records or mix other resource types. Review requires `collections.view`; apply additionally requires `collections.edit`. Definitions with slug `products` or `orders` also require `commerce.view` for reading and `commerce.configure` for definition mutations, matching the ordinary collection editor. Apply uses the exact `template-collection-instances-v1:<sha256>` review token; `scanned.collections` identifies the bounded definition inventory.

Compatible upgrades merge presentation and the pinned template baseline, preserving author-only changes. Field IDs, keys, types, required/unique constraints, options, references, defaults, validation and unknown field semantics cannot be changed silently; incompatible changes report bounded values-free `SCHEMA_INCOMPATIBLE` paths. Labels, help text, order and admitted frontend design data are presentation. Current public permissions, status, name/slug, route patterns, unknown operational metadata and all entries remain independent. This operation does not migrate entry values, publish content or change public access. Legacy definitions without a recorded baseline remain blocked. Inspect per-resource results and warnings; no automatic replay or cross-definition transaction is promised.

Authenticated collection definition responses carry a response-only `collection-v1:<sha256>` token. Ordinary PATCH accepts optional `expectedVersion` for compatibility with legacy callers, while retaining guarded current-snapshot admission. New editors should return the loaded token. A stale definition returns409 `COLLECTION_DEFINITION_CONFLICT` and requires reload. Entry `record-v1` tokens have a separate scope.

`GET /api/admin/sites/:siteId/collections/:collectionId/design-versions` returns `{siteId, collectionId, currentVersion, pagination, revisions}` under the read permissions above. Summaries contain only `id`, `createdAt`, `operation`, nullable `templateId`/`targetRevisionId`, and `hasPinnedBaseline`; historical design snapshots, records, public/operational policy and actors are private. Newest-first `offset` is0–1,000,000 and `limit` is1–100 (default100); follow `pagination.hasMore`/`nextOffset`. SDK: `listAdminCollectionDesignVersions`.

`POST /api/admin/sites/:siteId/collections/:collectionId/design-versions/:revisionId/restore` requires the read/edit permissions above and exact `{expectedVersion}` with the current collection token. It restores compatible presentation and baseline into the latest definition and saves the preceding design privately under the same guard.200 returns `{siteId, collectionId, restoredFromRevisionId, collection, completionWarnings}`; `collection.version` is the new definition token.409 `COLLECTION_DEFINITION_CONFLICT` requires reload;422 `COLLECTION_TEMPLATE_SCHEMA_INCOMPATIBLE` blocks semantic changes;503 `COLLECTION_DESIGN_HISTORY_UNAVAILABLE` refuses unavailable private recovery. Inspect audit/cache completion warnings after a committed result without replay. SDK: `restoreAdminCollectionDesignVersion`. Recovery responses are private/no-store.

Canonical `027_collection_design_revisions.sql` and the matching guarded repository are required. Source declarations and local acceptance do not prove canonical deployment, authenticated browser behavior or a custom frontend integration.
