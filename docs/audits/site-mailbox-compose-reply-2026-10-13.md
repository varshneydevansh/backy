# Site mailbox compose and reply source acceptance

The existing Settings mailbox workspace now supports explicit plain-text compose and reply, up to 50 distinct recipients across To/Cc/Bcc, and at most 10 regular outgoing attachments totaling 2 MiB. The sender is always the selected server-owned site binding. A reply carries the exact source folder and UID; Backy verifies source membership before Hostinger copies its Message-ID/References and flags it Answered. Hostinger accepts sends with HTTP 204 and saves a copy to INBOX.Sent; provider acceptance does not prove recipient delivery.

Private Owner-cookie admission remains mandatory. Compose also requires `settings.configure`; all other mailbox operations require both `sites.view` and `settings.view`. Explicit credential headers are refused before usage or provider access. Cookie writes require the trusted admin Origin. Public OpenAPI exposes field contracts only, never configured mailboxes, addresses, provider resource identities or credentials.

The new actions are under `/api/admin/sites/:siteId/settings/mailboxes/:bindingId`: `POST /send`, `GET /send-attempts`, and `GET /messages/:uid/thread?folder=...&page=...&perPage=...`. The SDK exposes `sendAdminSiteMailboxMessage`, `adminSiteMailboxSendAttempts` and `adminSiteMailboxThread` with isolated Owner-cookie transport.

Outgoing attachments are locally retained base64 draft content until an explicit Send. The backend rejects path/control filenames, invalid/noncanonical base64, excessive file count or aggregate size, unsupported input fields and duplicate JSON members, including escaped duplicates. Message text is bounded to 256 KiB UTF-8; subject to 998 UTF-8 bytes and JSON requests to 4.4 MB. No raw message/attachment content is retained in the send journal.

Migration 029 adds the private PostgreSQL send journal. Atomic insertion under an exact site/binding/idempotency key permits one provider execution; the normalized message plus bound provider mailbox/address fingerprint prevents key reuse with altered content or identity. Accepted, rejected, pending and uncertain attempts return the existing outcome on replay. Pending or uncertain attempts are never automatically resent. A network error, provider 5xx, invalid send response, or lost outcome persistence must be investigated through send history and Sent before any separately authored message. The database prevents changing duplicate identity or settled outcomes, deleting evidence, and browser-role access; service_role TRUNCATE is revoked. Demo mode uses a private atomically persisted file with an exclusive writer lock. Site deletion must retain duplicate evidence rather than silently remove it.

Thread inventory is explicitly bounded: it projects metadata for direct Message-ID/In-Reply-To relationships in the selected folder. The official provider has search and reference fields, but no native conversation endpoint. `searchPagination` counts candidate pages and the projected message list excludes unrelated body substring matches. Other folders and deeper branches can contain further related messages; this is not a claim of a full cross-folder conversation. Text reading and marking Seen remain separate explicit actions. Native mailbox and alias creation use the separate account API and exact existing free-plan bindings; see [management source acceptance](site-mailbox-management-2026-10-13.md).

These Backy bounds preserve room for base64 JSON and escaped text; larger provider-supported files need a separate managed-reference or streaming design.
