# Native mailbox and alias management source

Backy now exposes explicit Owner-only account management under `/api/admin/sites/:siteId/settings/mailbox-management`. The root GET reports configuration readiness and reviewed existing-domain hPanel links. A selected management binding supports POST `/inspect`, POST `/mailboxes`, POST `/aliases`, and GET `/attempts`. Inspection and creation require `sites.view`, `settings.view`, `settings.configure`, an active Owner cookie session and trusted admin Origin; API keys and explicit credential headers are refused. History requires both view permissions and the Owner cookie.

This integration uses the documented separate account API at `https://developers.hostinger.com`, not the mailbox-scoped API at `https://api.mail.hostinger.com`. Configure `BACKY_HOSTINGER_ACCOUNT_API_TOKEN` separately and `BACKY_HOSTINGER_MAIL_MANAGEMENT_BINDINGS` with explicit `id`, canonical `siteId`, `domain`, `orderId`, and a reviewed existing-domain `dashboardUrl` under `https://hpanel.hostinger.com/emails`. Omitting the account token/order keeps native controls disabled while the domain dashboard handoff remains usable. No token is created or copied from the Mail API config. Domains and provider order/mailbox identities are server-owned; creation requests cannot supply them.

The adapter verifies the exact order/domain using the documented exact-domain orders filter, reads the current plan and complete bounded mailbox/alias inventories, and requires an active `hostinger_free` order with no trial or pending upgrade. Mailbox capacity is the lesser of existing seats and domain mailbox quota minus current mailboxes. Alias creation checks both domain and per-mailbox quota and requires the target to match an existing explicitly registered site/domain inbox binding. Other or unverifiable plans/capacities fail closed. The adapter has no purchase, upgrade, password-change, token-creation or DNS operation.

The primary provider schema documents mailbox creation as `POST /api/mail/v1/orders/{orderId}/mailboxes` with `local_part` and `password`, and alias creation as `POST /api/mail/v1/mailboxes/{mailboxId}/aliases` with `local_part`; both return 201 resources at the top level. Local parts are at most 50 lowercase characters with the provider's documented letter/digit, dot, underscore and dash rules. Passwords are 8–50 non-space Latin characters with upper/lowercase, number and symbol. Passwords are transient request data only and are cleared from UI fields immediately after dispatch. They never enter request fingerprints, durable records, history, responses or audits.

Migration 033 creates a private site/binding/idempotency journal. Creation identity includes operation, exact bound order/domain, desired local part and registered alias target; it deliberately excludes passwords. Replaying a mailbox creation with another password returns the existing outcome and never changes a credential. Changed creation identity under the same key conflicts. Pending/uncertain attempts cannot be replayed. Provider timeouts, 5xx and malformed successful creation responses remain uncertain; lost outcome persistence remains pending. The UI locks dispatched actions and offers explicit history plus hPanel investigation. Journal identity and settled outcomes are immutable, browser roles have no access, service-role TRUNCATE is revoked, and site deletion must retain duplicate evidence. New mailboxes are not automatically registered for inbox access; that is a separate explicit server binding.

Provider fixtures follow actual response envelopes, top-level resources, quotas and exact paths. No real provider request, provisioning, password/token change, permission grant, purchase, plan change or DNS mutation was performed.
