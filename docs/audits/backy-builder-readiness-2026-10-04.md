## What the requested frontend control means

The required workflow is: an AI reads Backy's contract, builds a custom frontend around it, registers concrete editable page/component structures, and the owner can subsequently edit those pages in Backy without modifying frontend source for every article or element. The owner can also export a precise compatibility report to an AI when registration and rendering diverge.

Two supported integration forms need explicit treatment:

1. **Editable composition:** a header, hero, footer, or page registers a concrete element tree, stable child IDs, properties, styles, geometry, breakpoint overrides, fonts/assets, bindings, animation configuration, and editable field mapping. The frontend maps the registered types back to its components. A logo, navigation link, hero heading, image, and button become individually editable only when registered as such. Each existing page must have a Backy-owned instance and route; registering one template does not import every hard-coded frontend route.
2. **Executable widget:** a chart, simulation, complex React illustration, or other application registers a versioned, reviewed module and schema/controls/fallback. Its internal implementation can use React/SVG/timers; the supported sandbox module contract exports mount, with optional update. It remains one canvas element unless its internal controls or nested edit model are explicitly exposed. Arbitrary bundled React source is not automatically converted into independent canvas children.

There should be a guided import preview listing imported pages, nested elements, editable fields, assets, references, opaque widgets, unsupported layout/animation behavior, and unresolved mappings before accepting an import. This is a product requirement, not a currently verified complete import wizard.

### Drag, position, resize, and responsive behavior

Backy already stores element IDs, geometry, nested children, styles, and responsive overrides. Registered concrete children are recursively selectable/draggable, in parent-local coordinates; tablet/mobile moves write breakpoint overrides. Children are clamped to parent bounds, cross-parent multi-drag is limited, and reparenting uses separate nesting/promotion controls rather than normal pointer drop. See apps/admin/src/components/editor/Canvas.tsx:2334,2577–2624,3583 and CanvasEditor.tsx:1436,4804. However, absolute-positioned wrappers remain involved even inside flex containers. A preserved React flex/grid declaration is not proof of native flow layout, intrinsic sizing, or responsive reflow.

Completion requires each exposed child to be selectable through both canvas and layers; move/reorder/reparent with clear parent coordinates; resize and edit constraints; preserve stacking, grouping, snapping, locked elements, undo/redo, and breakpoint overrides; then save/reopen and render the same intended layout. Arbitrary positioning needs an explicit free-position mode. A flow container should use flow/reordering or deliberate mode conversion rather than silently changing its layout semantics. Full-width backgrounds and constrained reading columns must be separate settings. Desktop geometry scaled down uniformly is not sufficient mobile layout proof.

### Animations, tables, graphs, and executable content

Animation authoring exists: fade, slide, scale, bounce, rotation, and custom from/to objects, with load/scroll/hover triggers and motion tokens. The default public runtime uses GSAP and ScrollTrigger. Native data figures use shared React with SVG/HTML and inline JSON/CSV or scoped public-read collections; they do not depend on Collabora or Google Docs. The currently executed trusted rich mappings are rounds and line/bar/table; other registry entries can still display a static fallback.

These are different capabilities. A scroll fade is an element animation. A Cactus-style evolving SVG illustration is a stateful widget. A data chart needs data validation, access policy, complete pagination, loading/error handling, labels and accessible values. The frontend must implement the corresponding runtime, not merely preserve metadata or a CSS class. No arbitrary-language execution environment is established by a code highlighting block.

The actual production animation functions were executed with fake DOM/mocked GSAP calls: authored to:{x:150,opacity:0.4} produced x:0,opacity:1; hover fadeIn initialized invisible but emitted no visible destination; scroll without a scrollTrigger object emitted a load tween. These are proven generated-tween defects, with browser-visible consequences still requiring a focused runtime check. The AnimationBuilder preview is a blue CSS box, not faithful execution on the selected layer. The runtime also scans once on mount, has no explicit reduced-motion branch, uses mouse hover listeners, and kills all ScrollTriggers on cleanup. There is no complete visual multi-step timeline/state graph or automatic imported React/CSS animation conversion. These need targeted runtime and accessibility verification before claiming robust animation portability. See apps/public/src/components/AnimationHydrator.tsx:118–212 and apps/admin/src/components/editor/AnimationBuilder.tsx:29–116.

### Required AI-readable mismatch report — not yet implemented completely

Backy already exposes handoff, manifest, OpenAPI, editable maps, composition handoff, and connection diagnostics. The connection route checks reachability, probe declarations, and presence of required HTML attributes. It does not verify every element ID, node schema, rendered property, font, binding, layout mode, animation, or interaction. See apps/public/src/app/api/admin/sites/[siteId]/custom-frontend/connection/route.ts:543–554.

A proper report needs persisted frontend capability declarations plus observed checks, separated into supported, unsupported, fallback, missing, and unverified states. Every mismatch should include site/route/revision, template and component key/version, element ID, property or content path, breakpoint, expected value/behavior, observed result, evidence/confidence, impact, responsible side, and suggested repair. It must be downloadable/copyable as secret-free JSON and readable in an Issues panel with links to the affected element. Structural differences, visual differences, and functional failures should be distinguished; subjective design differences are not automatically API incompatibilities.

Example **proposed** issue payload, not a current endpoint response:

    {
      "code": "renderer.rich-node.unsupported",
      "route": "/blog/sample",
      "elementId": "article-body",
      "contentPath": "props.content[3]",
      "requiredCapability": "richText.data_figure",
      "expected": "interactive line chart with accessible values",
      "observed": "node omitted",
      "status": "unsupported",
      "repairOwner": "custom-frontend",
      "suggestedAction": "Implement the shared rich-node renderer and verify this route"
    }

Build this into the shared parent editor and site connection workspace. Blog/product/page views should consume it rather than building separate compatibility systems.

## Site login segregation and public access

Today, a user can belong to multiple teams with different team roles. Site access is primarily attached to its team; global module permissions and user overrides also apply. To separate two independently managed websites using the current model, each needs deliberate team ownership and membership. A common team grants team-level access across its sites. Adding siteId to the Users URL only provides navigation context; new-user creation does not assign a per-website role. Owners retain global workspace access by design; admin API keys also need explicit scoping if they are to be given to external agents.

This is not a demonstrated cross-site exploit: 31 repository-level allow/deny checks passed for the existing model. It is a mismatch between the current authorization model and the requested independent website roles. Public visitors, buyers and members need a separate identity/entitlement design; a contact record, local comment identity hint, or operator account does not supply that platform.

Public files can be delivered normally; private files can be delivered through expiring signed URLs authorized by admin media permissions. That does not establish a specific customer's right to a file. Media folder/tag/page/post bindings organize assets and track usage; they are not reader authorization rules. Approved public comments must exclude private author data, and public-read collections need deliberate schemas/projection and publication policy.

## Product completion standards

A page is complete when its visible actions, API persistence, loading/empty/error states, permissions, references, and public consequences work. API support, editor support, default public renderer support, custom frontend support, provider configuration, and live verification are separate states and should be visible separately.

The owner-facing editor should provide a clear layers tree, contextual inspector, writing workspace, media picker, reusable components/templates, responsive preview, undo/history, save status, preview/publish controls and focused issue list. Advanced raw schemas, API traces and provider diagnostics should be secondary workspaces. Registered complex components need a management UI for schema/defaults/nested children/versions, not just an insertion list and raw JSON.

The comparison bar is practical: Wix distinguishes collaborator/content permissions and Squarespace distinguishes contributor permissions and comment management. Backy should combine those clear workflow boundaries with its headless contract; it does not need to recreate every commercial platform application to publish a personal website. Reference documentation: [Wix CMS custom roles](https://support.wix.com/en/article/cms-formerly-content-manager-creating-custom-roles-and-permissions), [Squarespace contributor permissions](https://support.squarespace.com/hc/en-us/articles/206537297-Contributor-roles-and-permissions), [Squarespace blog comments](https://support.squarespace.com/hc/en-us/articles/205816108-Blog-comments-and-simple-likes).
