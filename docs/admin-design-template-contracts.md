# Admin design and template API contracts

The standard site OpenAPI document describes the existing authenticated design and template handlers. The SDK exports generated request/response types and retains its existing convenience methods.

`GET /api/admin/sites/{siteId}/templates` requires `pages.view`. It resolves site ID or slug to canonical identity and returns saved templates, version metadata, clone bodies, per-type groups and the unfiltered total count. Known `type` values are page, blogPost, form, product, collection and section; unknown type values are ignored. `search` is a trimmed case-insensitive substring filter over ID, name, description and route. This endpoint returns the full matching registry without pagination. Version readiness reports authored metadata completeness, not live frontend verification.

`POST /api/admin/sites/{siteId}/frontend-design` requires `sites.configure`, with the same fresh authorization and site boundary as the existing route. Its actions are:

- `import-frontend-contract`: normalize `frontendDesign`, `contract`, `design`, or `manifest.site.frontendDesign` / `manifest.data.site.frontendDesign` against saved state. Direct `site`/`data.site` envelopes and action aliases `import`, `connect-frontend`, `connect-custom-frontend` remain supported. Multiple supplied direct payloads follow the handler's precedence: frontendDesign, contract, design, then manifest. URLs remain declarations; the handler does not fetch or certify a frontend. Invalid runtime declarations fail with 400 before persistence.
- `capture-content-template`: require a known resource type and resource ID; canonical page, blogPost, form, product, collection and section types and existing plural/legacy aliases are supported. Resource reads are site scoped. Optional collection ID/slug selects the product record collection; optional template ID/name/route, source, binding hints and editable map describe the captured template.
- `capture-site-defaults`: capture existing theme/navigation and at most the first twelve listed pages. It does not scan a custom frontend or capture every authored page.

Imports and captures use the existing template history persistence. A history conflict returns 409; callers reload before retrying. Existing admin GET/PATCH design operations now reference the actual admin response envelope, rather than the public design response requiring schemaVersion and capabilities. The public envelope remains unchanged.

SDK methods: `adminTemplates`, `adminFrontendDesign`, `updateAdminFrontendDesign`, `importAdminFrontendDesign`, `captureAdminSiteDefaults`, `captureAdminContentTemplate`, and the additive typed `runAdminFrontendDesignAction`. Admin response aliases directly retain generated envelopes. Existing convenience input shapes remain compatible. Additional JSON metadata is allowed; input normalization can ignore unsupported fields and does not promise arbitrary input preservation.

Verification: `npm run test:admin-design-templates --workspace=@backy/public` executes the actual handlers, normalizer and registry with demo/repository storage adapters and authorization/delivery fixtures. It validates response/request schemas, early 401/403 denials, ID/slug resolution, all capture resource kinds, import aliases, nested versioned component/animation/responsive data, invalid runtime, scoped missing content, and 409 conflicts. SDK generated type assertions and `test:design-templates` exercise typed variants and transport. These checks do not certify PostgreSQL persistence, live operator authorization, deployed browser behavior, or full API contract coverage.
