# Reusing existing website media in the shared editor

Page and blog create/PATCH handlers admit explicit managed media identities against the current canonical site's catalog before writing content, revisions, reference metadata, or audit followups. Database-backed document saves revalidate those identities inside the same transaction that commits content and its media links. The same identity grammar powers repository reference indexing, including editor asset/font/download identities, asset lists, content documents, metadata and featured images. Missing IDs and IDs belonging to another site produce `400 INVALID_EDITOR_MEDIA_REFERENCE`, with the submitted `mediaId` and a JSON-pointer `path`; the response does not reveal another site's identity or asset details.

Native media IDs are UUIDs. Demo catalog IDs (including the existing `media-demo-hero` asset) remain valid only within their owning demo site. External image/font URLs without managed IDs and separate font/theme token names remain editable. Captured templates using valid same-site managed assets can still create page/blog content and retain revision provenance.

Reusing a post-owned asset on a page adds the page reference without changing the asset ID, original `scope`, `scopeTargetId`, original post references, URL, creation time, metadata or bindings. Repository sync now completes and validates media pagination before any reference-index writes, with the existing inventory bound of 100,000 assets. Media deletion also inspects saved page/blog/collection content; an ordinary referenced DELETE remains `409 MEDIA_IN_USE` before storage-provider access.

## Database save boundary

The public runtime decorates page/post create, update, publish, archive and delete, and collection-record create, update and delete (including the scoped `withRecordWriteLock` writer). These paths acquire the existing site-media advisory admission and use transaction-bound repositories for both document and reference writes. Native guarded page/post baseline revisions participate in that transaction, including timestamp-omitted HTTP saves. Index failures roll back the admitted content, baseline revision and reference changes. Reference updates patch only their own `pageIds`, `postIds` or `bindings` metadata key, preserving unrelated author metadata.

Storage/delete and document admissions share the existing two-guard bound per adapter. Contention returns `503 MEDIA_STORAGE_MUTATION_BUSY`, `Cache-Control: no-store`, and `Retry-After: 1`; the server does not retry a write automatically. Unsupported database protection returns `503 MEDIA_STORAGE_LOCK_UNAVAILABLE` before mutation. A status-only draft/archive PATCH can withdraw legacy content with missing media; authoring new references or publishing still requires valid same-site identities. Explicit referenced-delete overrides retain their existing separately authorised behavior.

## Composition imports and shared-section refreshes

The decorated runtime now passes admitted page/post/record writers into the existing top-level **SERIALIZABLE** composition-import and reusable-propagation transactions. These transactions acquire the same site-media admission before site locking and retain fresh reviewed inventory, source/target expectations and native revision history. Imported page/blog drafts and propagated page/post/product content validate managed media and commit their reference indices on the same connection. A late index failure rolls back all the aggregate’s content/history/design/audit writes that participate in its transaction. Reusable propagation no longer relies on best-effort HTTP indexing after commit. Existing independent cache/audit/webhook followups retain their separate completion-warning boundary.

Admitted content methods refuse writes to another site. The callback repository aggregate is trusted server code, not a universal sandbox for every raw site/media/design method it exposes. Raw native propagation callers receive admission locking but require the public runtime decorator for the validated reference-index guarantee. Composition provider plumbing now uses the actual adapter type and refuses unsupported admission before SQL.

## Collection imports and bulk operations

The decorated native backup import joins schema/record changes and essential media bindings in one admitted transaction. It retains the previous transaction isolation, full expected inventories, import-specific final uniqueness check and stale-snapshot conflict. It recognizes managed IDs in arbitrary schema-defined image/video/file fields, multi-file values, and nested design envelopes. External URLs retain the existing external-reference policy. The same schema-aware collector is used by individual record writers. Raw native imports hold admission but require the public decorator for the validated media index guarantee. Schema upserts also reconcile records preserved outside the import package against the final schema, on the same connection and before commit. Retained records are not rewritten, do not change timestamps, and remain absent from imported-record responses and mutation counters. Missing/foreign managed IDs or an index failure roll back the whole import. Reconciliation is sequential to preserve shared-asset bindings; it retains the complete media inventory bound and does not certify unlimited record counts or large-inventory performance.

Native bulk status/deletion keeps its sequential, per-record transaction boundary. It stops on the first failed write and reports committed IDs, skipped IDs, the failed target and records not attempted. A failure after a prior commit returns a partial result; it does not claim whole-batch rollback. Clients must refresh and retain unfinished selections rather than replay committed operations. Essential indexing runs only inside each admitted write. Independent audit/cache/webhook failures produce sanitized completion warnings after commit; these warnings do not provide an automatic retry queue.

## Editing media metadata

Native media PATCH acquires the shared guard before its fresh media read, reserved-field/folder/scope validation and metadata update. A caption/custom-metadata edit therefore cannot replay a reference list read before a concurrent admitted document save. The guard releases before independent audit/cache/webhook/organization enrichment. A committed edit stays200 with optional sanitized `data.completionWarnings`: `MEDIA_AUDIT_PENDING`, `MEDIA_CACHE_INVALIDATION_PENDING`, `MEDIA_WEBHOOK_DELIVERY_PENDING` or `MEDIA_ORGANIZATION_PENDING`. These codes report followup work; they do not constitute a durable retry queue or invite replaying an already committed edit. Explicit `pageIds`/`postIds` association replacement and existing target policy are unchanged.

## Limits

The joined boundary covers the decorated database runtime paths above. Direct/raw SQL repository callers and internal writers outside the explicitly decorated composition/propagation/collection-import boundaries are not certified to validate and index references. Media metadata PATCH uses the existing guarded callback; its independent followups are not one aggregate SQL transaction. Other business mutations or audit/cache/webhook followups outside these transactions are not made atomic by this change. Demo persistence retains its separately checked local behavior; cross-process demo atomicity is not claimed. The 100,000-asset bound remains explicit rather than a claim of unlimited inventory.

The fixture sessions and outbound audit/cache/webhook providers are synthetic. PostgreSQL evidence proves actual storage/repository/handler behavior, not deployed UI, provider delivery, signed/private media delivery, upload behavior, or production concurrency. No actual provider/upload/grant/production/frontend repository changes are made by these fixtures.
