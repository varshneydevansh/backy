# Atomic moderation and blocklist mutations

`BackyCommentRepository.moderateBatch` admits one site-scoped PostgreSQL transaction, locks the selected current rows, then computes moderation from those rows. Requested status/reviewer/reason or clearing reports remains the operator's explicit action. Other current fields—including authored content, thread, identity and retained block metadata—are preserved. Blocking current email/IP identities and updating all selected comments share that transaction. A later storage failure rolls back both the earlier selected updates and identity writes. The single-status and report-clear helpers use this same operation instead of composing independent writes from a pre-read comment.

Missing IDs, including IDs from another tenant, remain explicit `missingIds` outcomes. A successful selection can therefore update fewer rows than requested; this is an intentional missing-selection outcome, not a partially committed storage failure. Duplicate IDs are deduplicated, and result order follows selection order. PostgreSQL selection supports at most 100000 distinct IDs. Unsupported adapters or missing `moderateBatch` capability return `503 COMMENT_MODERATION_UNAVAILABLE`; no ordinary-update fallback is used. A removed current single comment or site returns a safe conflict. Explicit requested moderation is not a long-open-editor optimistic version protocol.

Standalone two-identity upserts and blocklist removal also use shared site admission. An upsert failure on the second identity rolls back the first. Removal uses a scoped returning delete inside one transaction and retains explicit missing IDs without exposing foreign rows. Success includes `data.completionWarnings: string[]` and `data.concurrencyBoundary`. A postcommit audit failure retains200 with `COMMENT_AUDIT_PENDING`. The SDK aliases the current generated blocklist envelope, and the admin adapter preserves warnings, displays a follow-up notice and does not automatically retry.

Demo status, batch, identity and blocklist mutations use one strict synchronous snapshot replacement. The writer validates current persisted inventory, preserves unknown envelope/row JSON, fsyncs/readbacks its temporary file and renames it before publishing changes to memory. Failed persistence leaves current memory and disk unchanged. Current site inventory is bounded to100000 comments. This provides single-process admission; there is no cross-process filesystem transaction claim. Existing legacy page/blog status-only HTTP methods retain their success projection and use the same atomic mutation helper; their safe 409/503 failures are documented.

After committed moderation, the existing activity/delivery/operator-audit follow-ups still produce safe completion warnings. Those warnings do not claim a durable queue, automatic replay or provider success. SQL mutation failures are precommit failures; provider/audit follow-up failures are distinct.

Evidence:

- Real isolated PostgreSQL baseline: a failed blocked-status update left two identity blocks committed; a second bulk update failure returned500 after the first row committed; a stale rejected-status helper replayed an older block reason over newer metadata. These are ordinary passing acceptance assertions after the repair.
- `npm run test:comment-lifecycle:postgres --workspace=@backy/db` extends actual helper/HTTP and independent SQL-connection tests to40 cases. The moderation portion covers those failures, successful selection/missing/tenant ordering, unsupported/missing capabilities, second-identity rollback, blocklist deletion rollback and postcommit audit warnings. Existing atomic-report/deletion regressions remain intact. The runner creates/removes its own socket-only cluster and never reads a configured database URL.
- `npm run test:comment-moderation-admission --workspace=@backy/public` covers actual demo store/HTTP mutations in owned scratch: atomic identity/status snapshot, missing scope, safe warnings, unknown extensions, failed persistence/corrupt inventory and a deleted preflight comment.
- `npm run test:comment-management-contract --workspace=@backy/public` covers actual handlers and schema validation using explicit atomic-adapter mocks; these supplement the independent SQL evidence.
- `npm run test:comment-management --workspace=@backy/sdk-js`, `test:comment-management-types`, and `node apps/admin/scripts/comment-deletion-outcome-smoke.mjs` cover SDK transport/typed parity and the actual bundled admin warning adapter, including legacy responses and no automatic retries.

This batch proves atomic moderation/blocklist mutations in local source and isolated storage. It does not certify deployment/load/provider behavior. A subsequent separately reproduced repair now enforces persisted identities during database intake; its current guarantees and54-check SQL proof are documented in [comment-submission-identity-admission.md](comment-submission-identity-admission.md). Demo remains single-process, and distributed spam/rate-limit enforcement is not certified.
