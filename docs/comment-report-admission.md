# Atomic comment report admission

PostgreSQL comment reports use the dedicated `BackyCommentRepository.report(siteId, commentId, { reason, requestId? })` operation. The repository starts a transaction, takes the same site row lock used by comment creation, moderation and subtree deletion, and rereads the scoped comment under a row lock. It checks the current published site, published page/post and report policy, then increments the current count and unions reasons. At count three the existing approved-to-spam threshold still applies. Reporting preserves current authored content, thread, author/visitor identity, block/rejection fields and moderation reviewer/time. A public reporter's `actor` is activity metadata, not moderation authority.

`reportRepositoryComment` uses a caller's pre-read comment only to identify the row. It never constructs an update from that snapshot and never falls back to the ordinary update method. A missing operation or non-PostgreSQL adapter fails before report mutation with `503 COMMENT_REPORT_UNAVAILABLE`. A deleted comment, changed non-approved status, withdrawn site/target or newly disabled reporting fails admission with `409 COMMENT_REPORT_CONFLICT`. The route returns constant sanitized messages with no-store. Its earlier public visibility and policy preflight still returns 404/403 when the resource is already unavailable. The success remains 201 with the existing sanitized public projection, report data and required completion-warning array.

After a committed repository report, interaction or configured delivery failures retain success with `COMMENT_ACTIVITY_PENDING` or `COMMENT_DELIVERY_PENDING`. These warnings do not promise automatic replay, a durable retry queue or provider delivery. A failed SQL mutation rolls back before those follow-ups run.

The demo store rereads and changes its current comment synchronously and rechecks reportability at that point. It preserves moderation attribution and rejects mutations made after the HTTP preflight. This is a single-process guarantee; it is not a cross-process filesystem transaction.

Evidence and commands:

- `npm run build --workspace=@backy-cms/core` then `npm run build --workspace=@backy/db` rebuild the actual repository used below.
- `npm run test:comment-lifecycle:postgres --workspace=@backy/db`: 30 actual handler/repository checks, including independent concurrent helper reports; blocked report admission behind moderation and deletion; reason union/threshold; current unrelated-field preservation; tenant, visibility and policy denial; actual route 409/503 and public projection; late SQL rollback; committed activity/delivery warnings. Always creates and removes its own socket-only PostgreSQL cluster and applies the actual migrations. It does not read a configured database URL.
- `npm run test:comment-report-admission --workspace=@backy/public`: nine actual demo store/route cases in disposable scratch data, including mutation at the JSON-await boundary after visibility preflight, persisted no-write denials and preserved moderation attribution.
- `npm run test:comment-management-contract --workspace=@backy/public`: 299 actual-handler/schema checks; explicit atomic-report adapter mocks cover conflict/unavailable and missing-capability errors. These adapter checks supplement the SQL evidence.
- `npm run test:comment-moderation-outcomes --workspace=@backy/public` and `npm run test:comment-security --workspace=@backy/public`: existing follow-up and public visibility regressions remain intact.
- `npm run test:comment-management --workspace=@backy/sdk-js`: 44 transport assertions, including typed report conflict/unavailable errors without automatic retries; `test:comment-management-types` verifies generated response parity.

The earlier actual isolated-SQL baseline persisted only one of two concurrent report counts/reasons and changed a newer rejected comment back to approved. Those assertions are now ordinary passing regression checks. This evidence covers the local source and isolated PostgreSQL/demonstration stores, not deployed traffic, cross-process demo workers, report rate limiting or live notification providers.
